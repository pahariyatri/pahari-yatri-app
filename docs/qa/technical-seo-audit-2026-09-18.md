Branch: `beta`. Scope: whole-site technical SEO, structured data, Core Web Vitals inputs, crawlability, manifest/PWA, AI-search files, internal linking. **The Parvati Valley Book (`data/books/parvati-valley-beyond-kasol.yaml` and its 16 chapters) was read for inspection only — zero bytes changed.** Verified with `git status --short data/` returning empty at the end of this session.

This session builds on the same-day UI/perf pass already recorded in `docs/qa/ui-performance-pages-audit.md` (hero-media removal on 7 pages, `/chapters` index removal). This report covers a broader, whole-repo technical-SEO pass on top of that.

## 1. What was already good

- **Sitemap architecture**: `app/sitemap.ts` already computes real `lastModified` dates from git history (not `new Date()`), separates static routes from dynamic Keystatic-backed ones, and already had precedent for redirect-instead-of-404 handling (`/books` intent, `/:region/stories/:slug` consolidation).
- **Canonical strategy**: every page either sets an explicit `alternates.canonical` or correctly inherits the root layout's relative `"./"` self-canonical default — verified empirically across 20+ sampled pages (static hubs, region/destination/place pages, stories, chapters, the dual `/books/[book]/[chapter]` ↔ `/chapters/[slug]` duplicate, which already self-canonicalizes to the chapter's true URL).
- **Structured data coverage**: `TouristTrip`/`FAQPage`/`BreadcrumbList` on chapters, `CollectionPage` on books, `TouristDestination`/`Place` on the regions hierarchy, a single `Organization` node referenced by `@id` everywhere instead of repeated — a genuinely well-designed schema graph.
- **Fonts**: all three families load via `next/font/google` (self-hosted, no external request) with `display: swap`.
- **Third-party scripts**: GTM loads via `next/script` with `strategy="afterInteractive"`, gated behind an env var so preview/local builds never fire it — not render-blocking.
- **AI-search groundwork**: `public/llms.txt` and `public/llms-full.txt` already exist, are accurate, and already correctly omit the (now-removed) `/chapters` index.
- **Internal link health for chapters**: every one of the 39 chapters already has at least one `relatedChapters`/`relatedStories` entry — an older audit (`content-inventory.json`) had flagged some chapters as link-orphans; verified fresh this session and that issue no longer exists.
- **robots.txt**: already allow-by-default with explicit allowances for major AI crawlers (OAI-SearchBot, PerplexityBot, ClaudeBot, Googlebot-Extended, etc.) — ahead of most sites on AEO.
- **Accessibility groundwork**: recent prior commits already fixed Lighthouse button-name/link-name/heading-order/label-content-name-mismatch failures site-wide.

## 4. Biggest organic-growth opportunities

- **Chapter-to-chapter internal linking is already structurally sound** (0 orphaned chapters) — the next lever isn't fixing broken links, it's *adding more of them* as new chapters ship, and building out topic clusters (e.g., a Mandi devta cluster: Kamrunag → Shikari Devi → Parashar, already partially cross-linked via the `/temples` cards).
- **`/scan-me` is a real, physical-world entry point** (printed QR) that was, until this session, actively damaging trust (fake address, dead form). It's fixed now, but it's also a good candidate to point directly at `/start` as the primary CTA going forward rather than a generic contact card, since `/start` is explicitly the site's designed orientation funnel for this exact kind of cold arrival.
- **Structured data is a real differentiator already** — `FAQPage` schema on every chapter is exactly what AI answer engines and Google's SGE-style results pull from directly. Expanding FAQ coverage to `/temples` and `/folklore` (currently plain card grids, no FAQ schema) would extend that advantage to two pages that already get the "people ask questions about this" kind of query.
- **`llms.txt`/`llms-full.txt` are already ahead of almost every competitor site** — very few travel/content sites have these yet. Keeping them accurate as content ships (as done here for `/start`) compounds that advantage cheaply.
- **The redirect consolidation pattern (`/books` → `/library`, `/chapters` → `/library`, region `/stories` → canonical `/stories`) is mature and correct** — the same treatment should be applied proactively to any future page-restructuring decision, rather than leaving a stale sitemap entry to be caught in a later audit.
